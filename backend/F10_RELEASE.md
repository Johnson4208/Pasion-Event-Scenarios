# F10 — Event Scenarios and evidence-led outlook

The existing Event Scenarios page defaults to private evidence-led research. Native category/factor choices and scenario comparison cards remain. The former worked examples and browser history require explicit Illustrative sample scenarios mode; they never become actual forecasts.

## API and records

- Member GET `/api/research/events` returns only the authenticated owner's immutable versions and manually recorded outcome archive. Owner query/body overrides are ignored. Admins cannot inspect another member's private studies through this endpoint.
- Member POST `/api/research/events` requires `question, event_definition, category, factor, focus, cluster_id, cutoff, maturity, outcomes` and optional `parent_id`. Clocks require offsets; cutoff cannot be future and maturity must follow cutoff. Each of 2–6 outcomes requires unique `id`, `name`, `resolution_rule`, `condition`, `assumption`, optional `weight`, and optional `evidence` links (`id, stance, relevance`). Stance is SUPPORTING/OPPOSING/MIXED and represents the author's relevance judgment, not automated sentiment. Weights must all be omitted or sum exactly to 100; no equal baseline is invented.
- Each save creates a new version with acceptance clock, original definition, cutoff, maturity, conditions, assumptions, judgments and embedded source snapshots. A parent must belong to that same member. Old research is never edited when sources change. Research saved more than 60 seconds after its cutoff is explicitly retrospective and cannot be presented as an original historical forecast. The 60-second tolerance is a UI clock tolerance, not a backtesting policy.
- Admin POST `/api/admin/events/evidence` admits one reviewed public-source claim with `claim_key, claim, provider, source_url` (HTTPS), `revision, input_type` (ACTUAL or PROXY), `input_policy, published_at, ingested_at, revised_at, reviewed:true`. A new revision creates a new ID. All source clocks must be nonfuture; revised_at cannot precede publication. known_at is at least the actual server acceptance time. No source-side date can backdate internal availability.
- Member GET `/api/research/events/evidence?origin=<offset clock>` returns the latest eligible claim revision per claim_key, with publication/ingestion/revision/acceptance clocks and actual/proxy policy. Equal-time ambiguous revisions are withheld. Referencing a future, ambiguous or superseded-at-cutoff claim fails rather than silently changing a research version.
- Member POST `/api/research/events/resolve` requires `version_id, outcome_id, observed_at, evidence_id, explanation`. The version must belong to the member, maturity must have passed, observed_at cannot be future, and a currently eligible ACTUAL source must have been published by observed_at. PROXY cannot resolve an event. Resolution is immutable and separate from the research payload, with its own known_at and source snapshot. Duplicate resolution is rejected. An archived result is a manual assertion, not calibration certification.

SQLite tables in accounts.sqlite3: shared append-only event_claims, private event_versions and event_resolutions with account foreign keys. API route policies restrict admission to admins and all research/archives to authenticated members. Responses omit account credentials, internal document paths and reviewer identities.

## Interpretation and limitations

All scenario weights carry ANALYTICAL_JUDGMENT_NOT_PROBABILITY. Probability status stays UNAVAILABLE_NO_CALIBRATED_EVENT_MODEL; no probability model or automatic evidence-to-weight scoring was added. F10 does not call Stock Analytics, Kelly or feasibility with weights. No change was made to the F05 calibration or F07 edge gates.

An author must define mutually exclusive, exhaustive resolution rules, including unresolved cases, and explain conditional mechanisms and assumptions. The backend validates structure, clocks, provenance availability and totals; it cannot prove arbitrary natural-language outcome rules are mutually exclusive or that a claim establishes an economic conclusion. Admin ingestion is explicit source review, not automatic verification of a URL. No live event/news feed or reviewed claims were supplied, so evidence starts missing and weights start unassigned.

cluster_id records related-event grouping for future evaluation. No calibration, Brier scores, probability certification, event-cluster train/test split or buy signal is inferred from the manual archive. Those require a separate sufficiently large, independently reviewed resolved dataset and a frozen model evaluation workflow. Account history lists the latest 200 versions; stored older versions are retained. F01 production identity/storage review remains necessary.
